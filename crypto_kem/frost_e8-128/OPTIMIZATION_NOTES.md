# Frost-E8-128 Cortex-M4 优化记录

本文记录 `crypto_kem/frost_e8-128` 的性能分析、修改依据、正确性验证和后续实测计划。基线数据取自 `FVE8_OPTViper.md`；旧 Frost-128 与 Frodo640 数据取自 `frost_benchmarks.md`。

## 1. 基线与对照

### 1.1 周期数

| 实现 | KeyGen | Enc | Dec |
| --- | ---: | ---: | ---: |
| Frost-E8-128 AES | 33,334,688 | 33,009,360 | 34,117,108 |
| 旧 Frost-128 AES | 41,864,953 | 41,207,731 | 42,420,862 |
| Frodo640 AES | 51,667,013 | 50,483,284 | 50,015,247 |
| Frost-E8-128 SHAKE | 48,575,067 | 49,610,532 | 50,718,263 |
| 旧 Frost-128 SHAKE | 56,090,120 | 57,157,413 | 58,370,504 |
| Frodo640 SHAKE | 70,927,342 | 70,538,467 | 70,070,433 |

Frost-E8-128 相对旧 Frost-128：

- AES 的 KeyGen/Enc/Dec 分别快 20.4%/19.9%/19.6%。
- SHAKE 的 KeyGen/Enc/Dec 分别快 13.4%/13.2%/13.1%。

Frost-E8-128 相对 Frodo640：

- AES 的 KeyGen/Enc/Dec 分别快 35.5%/34.6%/31.8%。
- SHAKE 的 KeyGen/Enc/Dec 分别快 31.5%/29.7%/27.6%。

这说明 E8 参数调整本身已经有效；当前目标是在不改协议格式和参数的前提下继续压缩实现开销。

### 1.2 已确认的主要原因

1. E8 版把 `PARAMS_N` 从旧 Frost-128 的 576 降至 512，矩阵规模从 `576^2` 降至 `512^2`，矩阵元素数量减少约 21.0%。汇编中的行字节数和点积展开次数已经同步为 1024 字节和 64 次，因此不存在“C 参数已改、汇编仍按旧 N 运行”的问题。
2. Frost-E8-128 的哈希/矩阵生成占比很高：AES 为 73.7%/77.1%/76.8%，SHAKE 为 83.0%/83.1%/82.7%。所以矩阵生成仍是绝对大头，也意味着只优化 codec 不会带来数量级变化。
3. `matrix_aes.c`、`matrix_shake.c`、`frodo.s` 以及生成器汇编已经沿用 Frodo/Frost 的 M4 分块生成和 `SMLAD` 点积路线。和 Frodo640/旧 Frost 比较后，没有发现一段遗漏的成熟汇编可以直接移植。
4. 非哈希路径仍有明确实现浪费：E8 codec 使用 64 位距离、逐 bit 读写、通用稀疏矩阵乘法及 64 项中转数组；10-bit/5-bit 密文打包仍走逐 bit 通用状态机。

## 2. 第一阶段：Frost-E8 codec 专用化

### 2.1 问题发现

`frost_e8.h` 原实现是参数通用写法：

- 每个 16-bit E8 标签通过逐 bit 函数拆分和写回；
- 编码时按完整的 8×8 基矩阵循环计算，虽然矩阵高度稀疏且 128 参数固定；
- `uint16_t` 接口先产生 `uint32_t[64]`，再逐项复制；
- 最近点解码使用 `int64_t`/`uint64_t` 的绝对值、选择、平方和比较。Cortex-M4 没有原生 64 位乘法与比较流水线，这会引入多指令序列。

### 2.2 修改思路

针对 128 参数加入编译期约束：`PARAMS_EXTRACTED_BITS == 2` 且消息矩阵固定为 8×8。在此约束下：

1. 每个 E8 block 恰好对应输入的两个字节，直接载入 16-bit label。
2. 按固定字段宽度 `1,2,2,2,2,2,2,3` 用移位和掩码拆出 `z0..z7`。
3. 展开 E8 稀疏基矩阵，直接写出八个坐标，去掉两重循环。
4. 解码后用固定移位直接合成 16-bit label，去掉逐 bit 写回。
5. `uint16_t` 编解码直接工作在目标数组上，去掉 `uint32_t[64]` 中转及复制。
6. 最近点路径降为 32 位。这里是安全的：`q=32768`、`alpha=8192`，单坐标舍入残差绝对值不超过 4096；八项平方和最大为 `8*4096^2 = 134,217,728 < 2^32`，比较差值也小于 `2^31`。

### 2.3 保持不变的性质

- E8 标签的 bit 顺序不变。
- E8 基矩阵、缩放因子、模 q 结果不变。
- 最近点候选、奇偶修正、tie 行为和常数时间选择结构不变。
- 公钥、密文及共享密钥格式不变。

## 3. 第二阶段：10-bit/5-bit pack/unpack 专用化

### 3.1 问题发现

Frost-E8-128 在 KEM 主路径只使用：

- `PARAMS_PK_LOGP = 10`；
- `PARAMS_U_LOGP = 10`；
- `PARAMS_V_LOGP = 5`。

原 `frodo_pack`/`frodo_unpack` 对每个元素维护 `w/bits/b` 状态并反复计算最小 bit 数、掩码和分支。该逻辑很通用，但不适合固定格式的大数组。

### 3.2 修改思路

- 10-bit 路径每 4 个系数固定映射为 5 字节。
- 5-bit 路径每 8 个系数固定映射为 5 字节。
- unpack 使用完全相反的固定移位恢复系数。
- AES 和 SHAKE 实现同步修改。
- 保留原通用实现作为其他 bit 宽度或非完整长度的回退，避免扩大接口行为变化。

这一修改覆盖：KeyGen 的公钥打包、Enc 的公钥解包和密文打包、Dec 的密文/公钥解包与重加密检查。

## 4. 验证记录

### 4.1 等价性模型

- 对全部 65,536 个 16-bit E8 标签穷举，新展开编码与原 8×8 基矩阵编码逐坐标一致。
- 对 10-bit 的 4096 项数组和 5-bit 的 64 项数组进行 1000 轮随机比较，专用 pack 输出与原 MSB-first bitstream 定义一致。
- `git diff --check` 通过。

### 4.2 指定平台编译

按项目约定只做 NUCLEO-L4R5ZI ELF 编译，不运行 QEMU、不上板：

```sh
make PLATFORM=nucleo-l4r5zi \
  IMPLEMENTATION_PATH=crypto_kem/frost_e8-128/frost128aes \
  elf/crypto_kem_frost_e8-128_frost128aes_test.elf

make PLATFORM=nucleo-l4r5zi \
  IMPLEMENTATION_PATH=crypto_kem/frost_e8-128/frost128shake \
  elf/crypto_kem_frost_e8-128_frost128shake_test.elf
```

结果：两个目标均成功生成。

## 5. 重新 benchmark 后如何判断

当前不能用仅编译结果虚构周期收益；应清除 Frost-E8-128 的旧 benchmark 条目后重新实测，并把新数据追加到本文。

预期特征：

- pack/unpack 优化应让三个操作都下降，Enc/Dec 通常更明显，因为其打包与解包次数更多。
- codec 优化主要影响 Enc/Dec，KeyGen 不调用 E8 消息编解码。
- AES/SHAKE 的非哈希代码相同，因此绝对节省周期应接近；SHAKE 总周期更大，百分比看起来会更小。
- 若收益很小，说明 74%–83% 的矩阵生成/哈希上限已经主导总体时间，下一阶段必须针对生成器本身，而不能继续堆叠 codec 微优化。

## 6. 后续候选与风险排序

1. **优先：量化与 pack 融合。** 当前先生成完整 `Bp_split/B_split` 再打包；可尝试按块量化后立即打包，减少一次大数组遍历。但 Dec 的常数时间比较和重加密检查需要重新设计接口。
2. **优先：矩阵生成微基准。** 分别测 `frodo_mul_add_as_plus_e`、`frodo_mul_add_sa_plus_e`、dither SHAKE 和 pack，确认实际剩余周期，避免被整体 hashing 百分比误导。
3. **中风险：SHAKE 行生成器状态模板。** 每一行都重新吸收 `row_index || seed_A`；只有在 fips202 实现允许安全、低成本复制预吸收状态且保持输入定义时才值得做。行号位于 seed 前面，不能简单预吸收公共 seed。
4. **中风险：AES 四行生成/点积流水化。** 当前已经四行批处理；进一步融合 AES 输出和点积会明显增加汇编复杂度，应以单函数实测为前提。
5. **暂不做：改变 `N/logq/logp/eta`。** 这属于参数与安全性设计，不是实现优化，不能仅为 benchmark 擅自修改。

## 7. 本阶段结论

应该开始 Frost-E8 优化，但它和 Viper 的性能结构不同：Viper 有较大的多项式算术优化空间，而 Frost-E8-128 已经使用成熟的 M4 矩阵汇编，且总体受哈希/矩阵生成支配。本阶段选择 codec 和固定宽度打包两个可验证、协议无关的缺口；是否继续进入生成器汇编重写，应由本轮重新 benchmark 和函数级测量决定。

## 8. 同步到 192/256/384/512

### 8.1 参数差异与同步策略

不能把 128 的常量原样复制到其他级别：

| 级别 | extracted bits | E8 block 字节数 | PK/U/V pack bits |
| --- | ---: | ---: | --- |
| 128 | 2 | 2 | 10/10/5 |
| 192 | 3 | 3 | 11/11/6 |
| 256 | 4 | 4 | 13/12/8 |
| 384 | 4 | 4 | 13/13/9 |
| 512 | 4 | 4 | 14/14/7 |

因此将 128 的专用实现推广成参数化快速路径：

1. 每个 E8 block 的总标签宽度恒为 `8*PARAMS_EXTRACTED_BITS`，所以恰好占 2、3 或 4 字节；直接按小端载入/写回一个 `uint32_t` label。
2. 八个 E8 字段的宽度仍为 `p-1,p,p,p,p,p,p,p+1`，使用由 `p` 计算出的固定移位拆分和合并。
3. 展开的稀疏 E8 基矩阵适用于全部参数，不再经过通用 8×8 循环和 64 项中转数组。
4. 全部级别统一使用经范围证明的 32 位最近点解码。192/256 原先仍是 64 位路径；384/512 原先已有 32 位距离计算，本次补齐直接 block codec。
5. 128 保留最快的 10-bit、5-bit 固定映射；其余级别使用 32 位 bit accumulator 快速处理完整的 5–14 bit 流，每次循环处理一个系数而不是逐 bit 状态机。

### 8.2 同步验证

- `p=2` 穷举全部 65,536 个标签；`p=3/4` 各随机验证 200,000 个标签。展开编码与原 E8 基矩阵结果一致，字段拆分后重新合成 label 也完全一致。
- 对 6/7/8/9/11/12/13/14-bit pack 各执行 10,000 轮随机等价比较，bit accumulator 与原 MSB-first 格式一致。
- 以下 8 个 NUCLEO-L4R5ZI test ELF 均编译成功：
  - `frost_e8-192`: AES、SHAKE；
  - `frost_e8-256`: AES、SHAKE；
  - `frost_e8-384`: AES、SHAKE；
  - `frost_e8-512`: AES、SHAKE。
- 仍未运行 QEMU、未上板执行。
